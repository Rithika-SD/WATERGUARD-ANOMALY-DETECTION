Review 2 Submission Report

SECTION 1: PROJECT OVERVIEW
WaterGuard is a prototype smart building web platform that detects abnormal water consumption and localises probable leak sources across 80 apartments in 4 residential buildings. It processes 15-minute interval sub-meter readings and generates explainable risk alerts for facility managers.

SECTION 2: PROBLEM STATEMENT AND MOTIVATION
Apartment water leaks often remain undetected until monthly billing cycles. In coastal flood-prone towns, external flood events mask internal pipe breaks, cause drainage backflow, and trigger simultaneous abnormal meter readings. WaterGuard provides automated detection with a 42-hour lead time, well within the 30-day billing cycle.

SECTION 3: OBJECTIVES AND PROPOSED SOLUTION
1. Detect anomalies at 15-min intervals using a hybrid statistical & rule engine.
2. Localise probable leak sources with evidence logs and disclaimer warnings.
3. Quantify compound coastal flood risk using the Coastal Flood Index (CFI).
4. Buffer and re-order streaming IoT meter data arriving delayed or out of order.
5. Provide human-in-the-loop workflows with decision and audit tracking.

SECTION 6: REVIEW 2 IMPROVEMENTS
A. COASTAL FLOOD INDEX (CFI)
- File: backend/ml/cfi_engine.py
- API: GET /api/cfi/sensitivity, POST /api/cfi/calculate
- Formula: CFI = alpha * R + beta * S + gamma * B
  R = Normalized Rainfall Risk (0-1), S = Normalized Storm Surge (0-1), B = Normalized Drainage Blockage (0-1)
  Constraint: alpha + beta + gamma = 1.0 (±0.001)
- Actual Configured Weights: alpha = 0.40, beta = 0.35, gamma = 0.25
- Sensitivity Profiles: Configured, Equal, Rainfall-Heavy, Surge-Heavy, Blockage-Heavy.
- CFI >= 0.75 adds +25 risk points. Graceful fallback to rainfall_flood_risk.
- Limitation: R, S, B use normalized 0-1 indices backed by 5 synthetic scenarios.

B. STREAMING METER DATA SIMULATION
- File: backend/ml/streaming_simulator.py
- API: POST /api/streaming/start, GET /api/streaming/status, POST /api/streaming/reset
- Dual Timestamps: event_timestamp (sensor clock) vs ingestion_timestamp (server clock).
- Deduplication: Unique key (meter_id, event_timestamp).
- Event-Time Ordering: Buffer re-sorted by event_timestamp after ingestion to protect rolling baselines.
- Lateness Window: Configurable threshold (default 120 min). Rejection reasons logged explicitly.
- Simulation Modes: normal, delayed (45-90m), out_of_order, duplicate, edge_cases.

C. ADDITIONAL EDGE CASES (8 TOTAL)
All 8 cases returned by GET /api/edge-cases and tested on Edge Cases page:
- EDGE-01: Legitimate High Consumption (Party)
- EDGE-02: Legitimate Night-Time Usage (Shift work)
- EDGE-03: Missing or Corrupted Meter Intervals
- EDGE-04: Sensor Stuck at Constant Value
- EDGE-05: Sudden Coastal Rainfall / Drainage Surge
- EDGE-06: Sudden Sensor Drops (Zero/negative flow -> Sensor Warning, NO false leak alert)
- EDGE-07: Null Bursts (6 consecutive missing intervals -> Data Quality Warning, false leak suppressed)
- EDGE-08: Seasonal Tenant Turnover (Occupancy 2->5 -> baseline scaled 2.5x, audit trail logged)
